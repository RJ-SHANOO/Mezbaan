### P1-24

Build the local operation log, with each write and its operation saved in one transaction. Lives in the Tauri shell (`apps/desktop/src-tauri/src/operation_log.rs`), same as P1-19/P1-22 — `packages/local-db` is still just the placeholder stub it's always been; the real local SQLite layer has consistently ended up in Rust, not that TS package. An `operation_log` table (id = client-generated UUIDv7, UNIQUE idempotency_key, operation_type, payload, synced_at reserved for P1-25) plus `record_once()`: one transaction that checks the idempotency key, runs the caller's actual write, and appends the log row — so a write and its log entry always commit or roll back together (rule 8), and retrying with the same idempotency key reruns nothing and creates no duplicate (rule 9). Generic by design, same as P1-22's pending-work primitive before it: there's no real business write to call it from yet (orders/cart are Phase 2), so it's exercised here with a synthetic write against a throwaway table. `list_unsynced()` is the minimal read-back P1-25's sync client is expected to build on; nothing here marks a row synced — that bookkeeping is P1-25's to design.

### P1-25

Build the sync client: batching, ordering, retry with backoff, and resume after a crash. `apps/desktop/src-tauri/src/sync_client.rs`: `run_sync_cycle()` batches every unsynced `operation_log` row (P1-24) in order, sends each batch through a `SyncTransport` trait (retrying with exponential backoff on failure, capped attempts), and marks accepted operations synced via `operation_log::mark_synced()`. "Resume after a crash" needs no special handling — nothing is marked synced until acknowledged, so a crash mid-cycle just leaves those rows for the next run to pick up again, proven by a test that fails a cycle on purpose and confirms a later one recovers the same operation. `ReqwestSyncTransport` is the real implementation; tests run against an in-memory mock so they don't need a live server (P1-26 doesn't exist yet). Local compile got stuck behind an environment-specific problem (reqwest as a new direct dependency triggered a from-source OpenSSL rebuild that hit Cygwin's perl shadowing Strawberry Perl on PATH, a Windows+git-bash dev-machine issue, not a code one) — verified clean on CI's Ubuntu runner instead (all 3 jobs green on commit 395345d).

### P1-26

Build the server sync endpoint with idempotency, validation and a per-operation result. `POST /sync/operations` in `api-pos`, device-token authenticated like `/devices/me` (`DeviceAuthGuard`) — tenant comes from the device record, not a user JWT, since a background sync cycle has no logged-in session. A `sync_operations` table (id = client UUIDv7 as primary key, UNIQUE per-restaurant idempotency_key) backs it: one bulk insert per batch with `ON CONFLICT (restaurant_id, idempotency_key) DO NOTHING`, so a retried batch (rule 9) upserts nothing new and every operation still comes back `"accepted"`, whether new or already recorded — verified with both a changed-id and an exact-same-id-and-key retry. `payload` is stored as the same JSON-encoded string the client sends (matches the Rust client's wire format, `apps/desktop/src-tauri/src/sync_client.rs`), not parsed — nothing interprets `operation_type`-specific contents yet (Phase 2). Tested at all three layers (service, RLS, HTTP e2e with real device pairing). One real bug caught along the way: `SyncModule` didn't list `DeviceService`/`AuditLogService`/`DeviceAuthGuard` as providers, so Nest's DI container couldn't resolve the guard — crashed the whole app at boot (not a catchable test failure) until fixed, same provider list `DevicesTerminalModule` already needed for the same reason.

### P1-27

Build downstream sync for menu, prices, staff and settings with versioned, signed snapshots, including each manager's PIN hash so approvals in P1-13 work offline. `GET /sync/snapshot` in `api-pos`, device-token authenticated like the upstream sync endpoint — returns `{ version, contentJson, signature }`, Ed25519-signed over `contentJson`'s exact bytes (never a re-serialization of the parsed object — Rust and JS JSON encoders don't promise the same key order, so the client must verify the literal string it received). `GET /sync/public-key` (no auth, it's a public key) lets ops fetch the verification key out of band to embed in the desktop build, rather than trusting a key delivered over the same channel it authenticates. Tested at both layers (service + HTTP e2e, including a tenant-isolation case and a round-trip signature-verification case). The client side — fetching, storing, and actually verifying a snapshot offline — is P1-27b, not this task; don't check P1-13 off from this alone, it also needs P1-27b.

### P1-27b

Depends on P1-19 (local SQLite) and P1-27. `apps/desktop/src-tauri/src/snapshot_sync.rs` fetches P1-27's snapshot and verifies its Ed25519 signature (pure-Rust `ed25519-dalek`, no OpenSSL) before anything downstream trusts it; `manager_pin_offline.rs` ingests the staff list wholesale (rule 11) and verifies a PIN with the exact same scrypt parameters and lockout thresholds (5 attempts, 15 min) as `packages/nest-core/src/manager-pin.service.ts`/`password.ts` — cross-checked against a real Node-generated hash, not just Rust round-tripping with itself, so a parameter mismatch couldn't silently pass. ### P1-28

Build per-terminal document number series. Format is `B{branch_number}-T{terminal_number}-{sequence:06}` — a two-part collision guarantee: `branch_number`/`terminal_number` are server-assigned once (at branch creation / device pairing), sequential and UNIQUE (`branches`/`devices` each got a new column + a DB trigger that auto-assigns the next one and a UNIQUE index as the real enforcement, not just the trigger's usual-case behavior — a genuine concurrent-create race fails outright rather than silently duplicating a number), so two terminals can never share a prefix; the trailing sequence (`apps/desktop/src-tauri/src/document_number.rs`) is a purely local SQLite counter needing no server round-trip, never reused or reset. Neither half needs to know what the other is doing, which is what actually makes two offline terminals unable to collide (rule 10). The trigger (not application code) assigns the number so every insert path — the real services and every existing test fixture — gets a correct number automatically; `BranchRecord`/`DeviceRecord` and their Zod schemas now carry the new fields. Doesn't wire `next_document_number()` into an actual invoice/receipt flow — nothing to wire into yet (Phase 2's P2-18 is that consumer).

### P1-30

Build the PostgreSQL outbox table and a worker that processes it with no broker. `outbox` table (`packages/db/src/schema/outbox.ts`, RLS tenant-isolated like every other tenant table) plus two halves in `packages/nest-core`: `OutboxService.record(entry, tx?)` for any api-* process to write a row inside its own business transaction (same `tx?` convention as `AuditLogService.record`, satisfying section 5's "the outbox row is written in the same transaction as the business change"), and `OutboxWorkerService` for `apps/worker` to actually process it — polls directly (no Redpanda/BullMQ, per this task's literal "no broker"), claims a batch with `SELECT ... ### P1-33

Add N+1 query detection and query plan checks for critical queries in CI. `createCountingDb()` (`packages/db/src/query-counter.ts`) counts every statement Drizzle sends via its logger hook — catches the N+1 shape (one extra statement per row) vs. a correctly batched query; demonstrated in `query-counter.test.ts` against restaurants/branches, the first real one-to-many relationship in the schema, since no "list with related records" endpoint exists yet (Phase 2+). `query-plan.test.ts` seeds realistic row volumes and runs `EXPLAIN` — inside the *same tenant context the real caller actually uses*, since RLS folds `current_setting(...)` into the plan and an unset context can make the planner misjudge an otherwise-index-favorable query — for three genuinely critical queries: the device-token check on every authenticated request, the outbox worker's claim query, and the sync idempotency lookup. Both are ordinary vitest files under `packages/db`, so CI's existing `pnpm test` step already runs them — no separate CI job needed. Found and fixed a real gap along the way: `devices.token_hash` and `devices.pairing_code_hash` had no index at all despite `validateDeviceToken` (every device-authenticated request) and `redeemPairingCode` querying by them directly — added both as part of this task, exactly the kind of regression these checks exist to catch. Also found and fixed two local-only test-hygiene bugs this surfaced: `query-plan.test.ts`'s bulk seeds didn't clean up after themselves, letting tens of thousands of rows accumulate across repeated local runs and slow down unrelated nest-core tests (now cleans up its own fixtures in `afterAll`); and `rls.test.ts`'s outbox super-admin test used a hardcoded literal id that collided across repeated local runs (now `randomUUID()`). Neither affects CI, which always starts from a fresh database.

### P1-35

Make sync send only changes, in compressed batches, with backoff and a random delay so terminals do not all reconnect at once. "Only changes" was already true (`operation_log::list_unsynced` only ever returns unsynced rows — P1-24). ### P2-01

Build categories and products with images, SKU, barcode and availability by branch. Backend only, by explicit choice — `apps/web` UI deferred until the catalog settles (variants P2-02, combos P2-03, pricing P2-04 are all still coming). `categories`/`products` tables (RLS-isolated, SKU/barcode unique per restaurant via a partial index so two NULLs never collide) plus `product_branch_availability`, an exclusion list matching feature_flags' convention: no row means available at every branch, a row only exists to record an explicit per-branch override. `imageUrl` is a plain reference column — the real upload pipeline is P2-44's job. New `menu.manage` permission (owner, branch_manager, super_admin). `CategoriesService`/`ProductsService` + controllers mounted in `api-admin`, same CRUD reference pattern as `BranchesService` (P1-17). Found a real, non-obvious gap while building this: **Postgres FK constraints are enforced by the migration owner, which bypasses RLS entirely** — so a product's `categoryId` FK alone would silently accept another restaurant's category, and the same is already true of existing FKs like `devices.branchId`. Fixed it for the new code with explicit tenant-scoped existence checks before every insert/update that references another tenant table (categoryId on products, productId/branchId on availability) — these run inside the caller's own `withTenant` context, where RLS actually does apply, unlike the FK check itself. Did not retroactively audit every pre-existing FK in the codebase; that's a broader gap worth a dedicated pass later, not this task's scope. Tested at all three layers (service — including the cross-tenant-FK-rejection cases above — RLS, and HTTP e2e added to `api-admin`'s existing `tenant-isolation.e2e.test.ts` so it's covered by the required CI check). Hit one local-only snag worth remembering: a new seeded permission needs the local dev DB actually re-seeded (`node packages/db/dist/seed-cli.js`) after editing `seed.ts` — the source change alone doesn't reach a long-running local Postgres. CI is unaffected; its "Seed roles and permissions" step always reseeds fresh.

### P2-02

Build variants such as size, and modifier groups with required and optional rules and min/max choices. Backend only, same scope choice as P2-01. `product_variants` (per-product, own SKU/barcode with the same partial-unique-per-restaurant convention as products), `modifier_groups` (restaurant-level, reusable across products), `modifier_options` (choices within a group), and `product_modifier_groups` (the join that attaches a group to a product). "Required/optional" and "min/max" are one pair, not a separate boolean: `minSelections` 0 means optional, `>=1` means required; `maxSelections` is nullable for an uncapped group. The min<=max invariant is checked at both the Zod boundary (`.refine()`) and inside `ModifierGroupsService` itself, since tests (and any future caller) can reach the service directly without going through the controller's parsing. Same explicit tenant-scoped existence checks as P2-01 everywhere a new row references another tenant table (productId on variants, modifierGroupId on options, both productId and modifierGroupId on the attach join) — RLS doesn't protect the FK itself, only these real queries do. `attachModifierGroup` is an idempotent upsert (reattaching just updates sortOrder). Tested at all three layers, with the variant/modifier e2e cases added to `api-admin`'s existing `tenant-isolation.e2e.test.ts`. Found and fixed a real, longstanding bug in `query-plan.test.ts` (P1-33) while its flakiness kept surfacing during this task's own test runs: its `ANALYZE` calls had been running as the restricted `mezbaan_app` role, which Postgres 16 silently lets no-op with just a WARNING (never an error) since that role doesn't own the tables — so the "fix" from P1-33 was never actually taking effect, and the test's pass/fail was riding on whatever stale statistics autovacuum happened to have produced. Fixed by running `ANALYZE` through a separate owner-privileged connection, and additionally made the outbox test's selectivity ratio less marginal (1-in-1000 pending rather than 1-in-100) and gave the devices test its own smaller seed count (500, not 5000 — it bulk-inserts through the P1-28 per-row trigger, which was pushing it toward its 30s timeout under load). Confirmed with three consecutive clean full-suite runs.

### P2-03

Build combos and deals with fixed and choice-based items. Backend only, same scope choice as P2-01/P2-02. `combos` (the deal itself) → `combo_slots` (positions like "Main"/"Side"/"Drink", each `kind: "fixed" | "choice"`) → `combo_slot_items` (candidate products per slot). A "fixed" slot's `minSelections`/`maxSelections` are pinned to 1 by `ComboSlotsService` regardless of what's passed — there's no meaningful choice count for a slot that was never a choice — and `ComboSlotItemsService.attach` rejects adding a second, different product to a fixed slot outright (a "choice" slot has no such limit; the customer picks within its min/max from however many items the menu offers). Reused modifier_groups' min/max pair convention from P2-02 rather than a separate required/optional boolean, and the same `onConflictDoUpdate` idempotent-attach pattern from P2-01/P2-02's join tables. Same explicit tenant-scoped existence checks everywhere a new row references another tenant table (comboId on slots, comboSlotId/productId on items) — RLS doesn't protect the FK itself. Tested at all three layers, with combo e2e cases (including the fixed-slot-rejects-a-second-item check) added to `api-admin`'s existing `tenant-isolation.e2e.test.ts`.

### P2-04

Build versioned price lists with branch, order type and time-based pricing. Backend only, same scope choice as P2-01/02/03 — the first consumer of this (P2-18's invoice generation) doesn't exist yet either. `price_lists` is genuinely versioned, not just labeled that way: `version` is sequential per (restaurant, name) via the same BEFORE INSERT trigger pattern as P1-28's branch/terminal numbers, and once a list's status moves to "published" neither it nor its `price_list_items` rows (`unitPriceMinor` as `bigint`, rule 5 — never a float) are ever mutated again; a price change is always a new row, both services reject any edit attempt once status isn't "draft". The three scoping dimensions are all nullable columns meaning "applies universally" on that axis: `branchId`, `orderType` (dine_in/takeaway/delivery — defined here first since P2-09 will need the same enum), and an `effectiveFrom`/`effectiveTo` timestamp window for the time-based half (intraday day-of-week/time-of-day scheduling was deliberately cut from scope — a reasonable extension later, not needed for a first version). `PriceResolutionService.resolvePrice` is the actual lookup: given a branch/order-type/moment-in-time and a product-or-variant, finds every *published* list that matches on all three axes and picks the best one by `priority` desc, then scope specificity, then most-recently-published — returns `null` when nothing's been priced for that combination, which is a real "not priced yet" state, not an error. Same explicit tenant-scoped existence checks as every other P2 catalog task everywhere a new row references another tenant table. `price_list_items` needed two separate partial unique indexes rather than one composite — a plain composite UNIQUE(price_list_id, product_id, variant_id) would never actually catch a duplicate product-only entry, since SQL treats every NULL as distinct from every other NULL. Tested at all three layers, including the resolution engine's own branch/order-type/time-window/priority/specificity test cases, with price-list e2e added to `api-admin`'s existing `tenant-isolation.e2e.test.ts`.

### P2-05

### P2-08

Add table transfer, merge and split — reuses P2-09's order/table model and P2-13/P2-14's state machine directly, needing no schema change at all (no migration). All three live on `OrdersService`/`OrdersController`, `pos.sell`-gated like every other order action, each wrapped in its own `withTenant` transaction:
- **Transfer** (`POST /orders/:id/transfer`, `{ targetTableId }`): moves a dine-in order (open or held) to a different, currently-free table — frees the old table, occupies the new one. No status change, so no `order_status_history` row; recorded via the audit log only (`order.table_transferred`).
- **Merge** (`POST /orders/:id/merge`, `{ targetTableId }`): two physical tables combined for one party. All of the source order's `order_items` move onto whichever order currently occupies `targetTableId` (their `order_item_modifiers` follow for free — they key off `orderItemId`, not `orderId`), then the source order is cancelled through the existing `open|held -> cancelled` edge (same `order_status_history`/audit trail a normal cancel gets) and its table freed. Rejects a currency mismatch between the two orders — merging items priced in different currencies would make `computeOrderTotal`'s single-currency `sum()` on the survivor meaningless.
- **Split** (`POST /orders/:id/split`, `{ targetTableId, itemIds }`): the reverse of merge — moves a named subset of one order's items onto a brand-new order at a different, currently-free table (part of a party splitting off). At least one item must stay behind (checked against the order's actual item set, not just a count) — moving everything is just a transfer, so that's rejected with a message pointing at transfer instead of a generic "bad request."
- Three new private helpers (`requireOccupyingDineInOrder`, `requireFreeTableInBranch`, `requireOccupiedTableOrder`) hold the repeated guards (dine-in + open/held, table-free, table-occupied). `create()`'s own inline table-free check was refactored to call the same `requireFreeTableInBranch` rather than duplicating it.
- Tested at both layers: `orders.service.test.ts` (6 new cases — transfer happy path + table-conflict/wrong-order-type rejections, merge happy path + no-order-on-target/same-table rejections, split happy path + empty/unknown-item/leave-nothing-behind rejections) and `apps/api-pos/src/orders.e2e.test.ts` (4 new cases — transfer/merge/split end to end plus a single cross-tenant 404 case covering all three). ### P2-14

Add hold and recall of orders, and running tabs for dine-in tables. Extends P2-13's state machine with a new `held` status — a parked ticket, not a finalized one: `open` → `held` (hold) and `held` → `open` (recall) are new legal edges, plus `held` → `cancelled` (abandoning a parked ticket outright); `held` → `closed` stays illegal by design, since billing always goes through the normal open state first. Holding/recalling never touches table occupancy — a table is "occupied" by whichever order is `open` *or* `held` on it (the dine-in table-conflict check in `OrdersService.create` was broadened accordingly), since a held ticket is still that customer's table, not a free one. New `OrdersService.hold`/`recall` methods and `POST /orders/:id/hold`/`recall` endpoints (api-pos), both `pos.sell`-gated, both recorded in `order_status_history` and the audit log like every other transition. "Running tabs for dine-in tables" is a read: `OrdersService.getTableTab` finds whichever order currently occupies a table (open or held), returns its line items (via P2-12's `OrderItemsService`) and a running total computed through `packages/domain` money functions (rule 5) — `null` order/items/total is a real "nothing open here" state, not an error. New `GET /tables/:tableId/tab` endpoint. Tested at all three layers: domain (every legal/illegal edge including the new ones), nest-core service (hold keeps the table occupied, a second dine-in order is still rejected while held, held can't close directly, recall of a never-held order is rejected, tab returns null-then-populated), and api-pos e2e (hold/recall/tab end to end, cross-tenant 404 on both hold and tab).

### P2-15

Add fire-to-kitchen by item or course, and tracking of what was already sent. `OrderItemsService.fireItems` takes either a named `itemIds` set or a `course` string (exactly one, enforced by `FireOrderItemsSchema`'s `.refine()` and again in the service itself) and stamps every *currently un-fired* matching item with `firedAt`/`firedByUserId` in one update. Firing by course only touches items with that course value on this order, not every item — and whichever target was given, an item that's already fired is simply skipped rather than re-sent: firing a course a second time after adding a new item to it only sends the new one, and firing a target where every item is already fired raises `ALREADY_FIRED` instead of silently no-op'ing (rule 16 — a caller who expects something to happen should hear about it when nothing did). `firedAt`/`firedByUserId` are nullable columns on `order_items` (migration 0024), not a boolean flag, so "already sent" carries its own timestamp and actor rather than needing a second lookup elsewhere — the same reasoning P1-14's audit log already established. New `POST /orders/:orderId/items/fire` (api-pos), `pos.sell`-gated like every other order-item action, recording an `order_item.fired` audit entry with the fired item IDs and course. **Explicitly out of scope**: a real "no money fields" kitchen ticket (rule 18) that a kitchen display or printer would consume doesn't exist yet — that's P3-02's job specifically; this task is only the POS-side record of what was sent and when, which P3-02 can read once it exists. Tested at all three layers: `contracts`' `FireOrderItemsSchema` (exactly-one-of-itemIds/course, non-empty itemIds), `order-items.service.test.ts` (fire-by-id, fire-by-course leaving other courses untouched, partial re-fire sending only what's new, already-fired rejection, cross-tenant 404), and `apps/api-pos/src/order-items.e2e.test.ts` end to end.

### P2-16

Prevent two terminals from silently overwriting the same open order on the local network. There is no branch hub yet (P2-36 through P2-39 are still unbuilt) — terminals talk directly to `api-pos` over HTTP, so "two terminals racing" today means two concurrent HTTP requests against the same order row, and the real fix at this stage is concurrency-safety at the database, not a hub-level sync protocol. Two complementary mechanisms, closing two distinct races that existed since P2-09/P2-13:
- **One order per table, enforced by the database, not just app code.** `requireFreeTableInBranch` already checked for an existing open/held order on a table before inserting/moving one there, but that's a read-then-decide check — two concurrent terminals can both read "free" before either writes. A new partial unique index, `orders_table_occupancy_idx` (migration 0025) on `orders(table_id) WHERE table_id IS NOT NULL AND status IN ('open', 'held')`, is the actual guard: the loser's `INSERT`/`UPDATE` now fails with a real unique-violation instead of silently landing a second order on an already-occupied table. `OrdersService.create`, `transferTable` and `splitTable` (the three places that write a `dine_in` order's `tableId`) catch that violation via the existing `isUniqueViolation` helper (`pg-error.ts`, from P1-15's onboarding slug-conflict handling) and translate it back to the same `TABLE_ALREADY_OPEN` `BadRequestException` the pre-check already raised — callers see one consistent error either way, whether they lost the pre-check race or the real one.
- **Row-level locking for concurrent mutations on the same existing order.** The index above only helps when a *new* table-occupancy conflict is being created; it does nothing for two terminals racing a transition on the *same* order (one closes while another cancels) or two terminals racing a cart edit on the same order. Every method that reads an order (or order item) then writes to it now takes the row lock first via `SELECT ... FOR UPDATE`: `OrdersService.transition` (close/cancel/hold/recall), `requireOccupyingDineInOrder` (the first read in transfer/merge/split) and `requireOccupiedTableOrder` (merge's target-order read), plus `OrderItemsService.requireOpenOrder` (shared by add/update/remove/fire). The second concurrent transaction now blocks until the first commits, then re-reads the *real* post-commit state before deciding — so racing close-vs-cancel on one order reliably ends with one winner and one `ILLEGAL_TRANSITION` rejection, never two silent, contradictory writes.
- Tested at both layers: `packages/db/src/rls.test.ts` exercises the new index directly at the SQL level (rejects a second open order on an occupied table, rejects it again while the first is merely `held`, allows it once the first is `closed`), and `orders.service.test.ts` fires two real concurrent service calls — `Promise.allSettled` on two `create()` calls targeting the same table, and on `close()`/`cancel()` racing the same order — asserting exactly one side wins and the loser gets a clean `BadRequestException`, not a crash or a silent double-write.
- **Explicitly out of scope**: this does not touch the eventual hub-based local-network sync model (P2-36 through P2-39) — once terminals can go fully offline and reconcile through a hub, that reconciliation will need its own conflict story (likely still anchored on this same unique index and the order's `updatedAt`/status, but with an actual merge/replay step this task has no reason to invent before the hub exists to carry it).

### P2-17

Show clear offline, syncing and price-list-version status on the POS screen. The offline/online half of this was already delivered by P1-29's `SyncStatusIndicator` (pending-operation count, online/offline, last successful sync) — unchanged here, and it already renders in both POS and kitchen windows. What this task actually adds is the "syncing" and "price-list-version" halves, scoped to the one sync that genuinely runs today: `PosScreen`'s own `sync_menu` call (the operation-log push-sync `sync_client.rs`/P1-25 drives is still never invoked from anywhere in the running app — its own `online`/`pending` readout is real, but it has nothing to report yet since nothing calls it).
- **"Price-list-version" is "prices as of {time}", not a counter**: `SyncSnapshotService.buildSnapshot` stamps `version: new Date().toISOString()` — the moment the server built this snapshot — not a monotonic edition number, and each cached price row already carries its own `price_list_id`/`price_list_version` per P2-04's resolution (different items can legitimately come from different price lists). A single screen-level "version" can only ever mean "how fresh is the whole snapshot," so that's what's shown, not an attempt to summarize per-item price-list versions into one number.
- **Persisted, not just held in React state**: `sync_status.rs` gains `record_menu_sync_version`/`get_menu_sync_version`, storing the version in `app_metadata` (same key-value store `pending_work.rs` and this file's own online/pending state already use) — set by `menu_commands::sync_menu` right after a snapshot is successfully ingested. - **Three distinct states, deliberately not collapsed into one**: `isSyncingMenu` (true for the duration of the in-flight `sync_menu` call) renders "Syncing prices…"; once settled, a known version renders "Prices as of {time}" regardless of whether *this* attempt succeeded or failed (a failed retry doesn't erase a perfectly good earlier version); only the terminal's very first-ever sync, still unresolved or failed with nothing persisted yet, renders "Prices not yet synced." - Tested at both layers: `sync_status.rs`'s own unit test (sets, reads, overwrites — same upsert convention as its other metadata keys) and three new `PosScreen.test.tsx` cases — the in-flight "Syncing prices…" state (using a manually-resolved promise rather than `renderAndFlush`'s usual settle-everything wait, specifically to catch it mid-flight), falling back to a persisted version when this session's own sync fails, and the true first-run "not yet synced" case. Every existing `PosScreen.test.tsx` case needed `getMenuSyncVersion` added to its mocked module and a `beforeEach` default (`resolves to null`) — `PosScreen` now calls it unconditionally on every mount, so an unmocked call would have thrown in every pre-existing test.
- **Rust side not locally compiled** (same pre-existing Cygwin-Perl/OpenSSL `cargo` issue P1-25/P2-11/P2-12 already documented on this machine) — reviewed by hand against the already-compiling `sync_status.rs` functions it extends line-for-line; CI's Ubuntu runner is authoritative.

### P2-18

Generate invoices with per-terminal numbers, using only domain calculations and a price version. This is the first real financial-ledger table in the codebase (rule 4: append-only, `invoices`' UPDATE/DELETE revoked from `mezbaan_app` same as `audit_logs`/`order_status_history`).
- **A second step after closing, not folded into it**: `InvoicesService.generate` requires the order to already be `closed` (`OrdersService.close`, P2-13) — closing is what actually locks further edits (`OrderItemsService.requireOpenOrder` already rejects mutating a non-open order); generating the invoice is the separate act of fixing a document number and a computed total against that now-locked content. Rejects outright if an invoice already exists for the order (no regenerating one in place — a real correction is future compensating-document territory, P2-24) or if the order has no items.
- **No new pricing happens here**: totals come from the order's own already price-list-versioned items (P2-12's snapshotted `unitPriceMinor`/`priceListId`/`priceListVersion` per item) through `computeOrderTotal` (now exported from `orders.service.ts`, shared with `OrdersService.getTableTab`) and `TaxCalculationService.previewCharges` (P2-05 — its own docstring already named this task as the real consumer). "Using only domain calculations and a price version" is satisfied by *not* re-resolving or re-pricing anything, only persisting a pure `packages/domain` computation over what was already locked in.
- **The per-terminal number is a new, deliberately separate counter from P1-28's.** P1-28 built `B{branch_number}-T{terminal_number}-{sequence:06}` with the trailing sequence as a purely desktop-local SQLite counter (`document_number.rs`) — by design, there's exactly one such sequence per physical terminal installation, with no server equivalent. But no real offline terminal sales flow exists yet to drive that counter (no login/cart-to-server wiring on desktop — P2-12's own notes), so every real invoice today is generated through this server path (`api-pos`). A new `devices.nextInvoiceSequence` column gives each device row its own counter server-side, incremented atomically via a plain `UPDATE ... SET x = x + 1 ... RETURNING x` (Postgres already serializes two concurrent writers on one row — no explicit `SELECT ... FOR UPDATE` needed). The branch/terminal number halves are the same already-unique `branches.branchNumber`/`devices.terminalNumber` from P1-28. **This is a real, documented gap, not silently papered over**: the two sequences (this one and the desktop-local one) are not reconciled, and can't produce colliding numbers today only because nothing else is generating real invoice numbers yet. Whichever task builds the actual offline terminal sales pipeline must resolve this before it can be trusted — most likely by retiring this server-side counter in favor of always generating the number locally and syncing it up, consistent with rule 8/9's "every terminal write goes to SQLite and the operation log first."
- `deviceId` is a required parameter to generation (not inferred) — a cashier's HTTP session carries a user token, not a device token (that's a separate P1-20 mechanism for sync/pairing), so there's no way to know which physical terminal issued a sale without the caller saying so. Validated: the device must belong to the order's own branch (`DEVICE_WRONG_BRANCH`) and must be `active`, not revoked (`DEVICE_REVOKED`).
- `documentNumber`'s UNIQUE index is scoped by `restaurantId`, not global — `branchNumber`/`terminalNumber` are each only unique *within* their own restaurant/branch, so two different restaurants' first branch and first device both legitimately produce "B1-T1-000001". Missing this the first time around caused every cross-tenant test to collide on a bogus global uniqueness violation; fixed before anything using it was committed.
- `appliedTaxRules` (the actual stacked tax rules used, not just the combined rate) is stored as `jsonb` for the receipt/audit trail, same convention as `audit_logs.metadata`/`outbox.payload` — no `.$type<>()` typing, matching this codebase's existing lightweight-jsonb convention; the service layer maps it to a typed shape at the boundary instead.
- `OrdersModule` provides its own copies of `TaxRulesService`/`TaxSettingsService`/`ServiceChargeSettingsService`/`TaxCalculationService` directly (same pattern it already used for `PriceResolutionService`) rather than importing `CatalogModule`, which would also pull every admin catalog-management controller into `api-pos` — "the POS and sync API," not admin catalog management (section 4).
- Tested at all three layers: `invoices.service.test.ts` (happy path incl. document-number format and computed totals, not-closed rejection, no-regenerate, no-items, wrong-branch device, revoked device, per-device independent sequences, cross-tenant 404), `rls.test.ts` (tenant isolation, the restaurant-scoped document-number index allowing the same number across tenants while still rejecting a true same-tenant duplicate, UPDATE/DELETE revoke), and `apps/api-pos/src/invoices.e2e.test.ts` (generate-then-fetch, the empty "no invoice yet" `null` state, not-closed rejection, cross-tenant 404) end to end.

### P2-19

Add cash, card, bank transfer and wallet payment methods, configurable by restaurant, including tips.
- **`payment_method_settings`** reuses `feature_flags`' exclusion-list convention: absence of a row for a method means "enabled," so a restaurant that hasn't configured anything at all still takes every method on day one (rule: never block a sale over a missing setting) — a row only needs to exist to turn one *off*. Restaurant-scoped, not branch-scoped — nothing in this task calls for per-branch payment differences, and adding that scoping with no real requirement driving it would be unearned complexity. `PaymentMethodSettingsService.set` upserts via `onConflictDoUpdate` on `(restaurantId, method)`, same pattern `FeatureFlagsService.setFlag` already established; `isEnabled` is the actual check a sale runs against (no row → `true`).
- **`payments`** is the second real financial-ledger table (after P2-18's `invoices`), same append-only enforcement (rule 4: UPDATE/DELETE revoked from `mezbaan_app`). Deliberately *not* unique-per-invoice — a single invoice can take more than one payment row (cash + card), which is exactly what P2-20 ("split payments across multiple methods") needs; this task only records each payment correctly on its own and makes no attempt to check that recorded payments sum to the invoice total, or to compute exact change. `tipMinor` is its own column, never folded into `amountMinor` — a tip isn't part of the sale (rule 6: never under- or over-report what a sale actually was).
- `PaymentsService.record` validates, in order: `amountMinor > 0`, `tipMinor >= 0` (both before touching the database), the method is currently enabled for the restaurant, and the referenced invoice actually exists (tenant-scoped, so a cross-tenant invoice id surfaces as the same `NotFoundException` a nonexistent one would, never a 403 that would leak existence).
- **Module placement mirrors P2-18's reasoning exactly**: `PaymentMethodSettingsController` (the admin-facing CRUD, same `menu.manage` permission tier as tax/service-charge settings) lives in `CatalogModule` for `api-admin`; `OrdersModule` (`api-pos`) provides its own copy of `PaymentMethodSettingsService` (no controller) purely so `PaymentsService` can call `isEnabled` without importing `CatalogModule` wholesale and pulling every admin catalog controller into the POS/sync process. `PaymentsController` itself is a new top-level `invoices/:invoiceId/payments` resource (not nested under `orders/:id/...`) — same reasoning P2-14's `TableTabController` already used for breaking out a resource that doesn't belong under a single parent path.
- Tested at all three layers: `payment-method-settings.service.test.ts` (default-enabled, disable/list, re-enable upserts rather than duplicating, per-tenant independence, audit), `payments.service.test.ts` (happy path with a tip, tip defaults to zero, multiple payments against one invoice, rejects non-positive amount/negative tip/disabled method, cross-tenant 404s, empty-list state), `rls.test.ts` (tenant isolation for both new tables, append-only revoke on `payments`), and e2e: a new cross-tenant case added to `api-admin`'s existing `tenant-isolation.e2e.test.ts` (matching that app's combined-file convention, unlike api-pos's per-feature files) plus a new `apps/api-pos/src/payments.e2e.test.ts`.

### P2-20

Add split payments across multiple methods, with exact change calculation. P2-19 deliberately left two things undone — "recording two or more payments against the same invoice" was allowed by the schema but never reconciled against the total, and there was no cash-tendering/change concept at all. This task closes both.
- **Reconciliation**: `PaymentsService.record` now locks the invoice row for the rest of its transaction (`SELECT ... FOR UPDATE`, the exact same convention P2-16 already established for order mutations), sums every payment already recorded against it (`sumPaymentAmounts` — a plain JS/bigint reduce over the rows rather than a SQL `SUM()`, since the row count per invoice is always small and this avoids any ambiguity in how a driver would represent a bigint aggregate), and rejects outright if the new `amountMinor` would push the running total past the invoice's own total (`AMOUNT_EXCEEDS_BALANCE`), or if the invoice is already fully paid (`INVOICE_ALREADY_PAID`). The row lock is what actually makes a *split* payment safe under concurrency — two terminals racing to record the last two halves of a bill can't both read the same "remaining" balance and both succeed; the second one waits, then re-sums against what the first just committed.
- **Exact change, cash only**: `RecordPaymentSchema` gains an optional `tenderedMinor` — what the customer physically handed over — rejected outright for any method other than cash (`TENDERED_ONLY_FOR_CASH`) and rejected if less than `amountMinor` (`TENDERED_LESS_THAN_AMOUNT`, that would mean the customer handed over less than what's being applied, not more). The server computes `changeMinor = tenderedMinor - amountMinor` and persists it on the payment row — a new `payments.changeMinor` column (migration 0028, `DEFAULT 0` so it doesn't blow up on rows already written by P2-19's tests) — never the caller's job to do that arithmetic. `changeMinor` is its own column, same reasoning as `tipMinor`: change given back is not part of the sale and must never be folded into `amountMinor` (rule 6).
- **New `GET /invoices/:invoiceId/balance`** (`PaymentsService.getBalance` / `InvoiceBalanceController`) — the running `{ totalMinor, paidMinor, remainingMinor }` a real split-payment UI needs to check before deciding the next method/amount, and the natural "empty state" (nothing paid yet, `remainingMinor` equals the full total) this task's own DoD calls for. Lives as its own top-level `invoices/:invoiceId/balance` controller, not folded into `PaymentsController` — it's a derived view over the invoice *and* its payments together, not a payment itself, same reasoning P2-14's `TableTabController` already used for breaking a resource out of its most obvious parent path.
- Tested at the service and e2e layers: `payments.service.test.ts` gained exact-change computation, `tenderedMinor` rejected for non-cash and when less than `amountMinor`, a genuine three-way split landing on a zero balance, overpayment rejection, already-paid rejection, and three new `getBalance` cases (initial, partial, not-found). `apps/api-pos/src/payments.e2e.test.ts` gained the same split/change/overpay cases over real HTTP.

### P2-21

Add split bills by item, by seat, by amount and into equal parts — four named modes, but really only two distinct pieces of real work.
- **"By amount" is already done.** Splitting a bill into custom, caller-chosen amounts is exactly what P2-19/P2-20's `PaymentsService.record` already supports: call it once per person with whatever `amountMinor` they're covering, and P2-20's balance reconciliation already stops anyone from overpaying. No new code for this mode — documented here so it isn't mistaken for a gap.
- **"By item" and "by seat" needed a real schema change**: a closed order could only ever carry one invoice (P2-18's `invoices_order_id_idx` UNIQUE index), which made separate checks for separate items structurally impossible. That index is gone; the real invariant moved to `order_items.invoiceId` (nullable, set once billed) — every item is billed on at most one invoice, checked in `InvoicesService.generate` itself rather than by a table-level constraint, since "has this order's single invoice already been made" stopped being a well-formed question.
  - `generate` now takes an optional `itemIds` — given, it bills only those (validated to belong to the order and be currently unbilled, `SELECT ... FOR UPDATE`-locked so two concurrent split calls can't both bill the same item, same convention as P2-16/P2-20); omitted, it bills every currently-unbilled item, same as before splitting existed. Totals are computed fresh for whichever subset is targeted — each split invoice gets its own correctly-computed tax/service-charge over its own items, not an arbitrary fraction of one combined total.
  - `splitBySeat` groups the order's unbilled items by `seatNumber` (items with no seat assigned share one "unassigned" invoice) and calls `generate` once per group; `splitByItems` does the same over caller-named groups. Both are thin loops — each `generate` call is its own transaction and its own document number, so there was no need to invent a new multi-invoice transaction shape.
  - `getByOrderId` now delegates to a new `listByOrderId` and returns the first result, kept only for backward compatibility with the pre-split single-invoice callers; the real list lives behind a new `GET /orders/:id/invoices`.
- **"Equal parts" reuses an existing domain primitive.** `packages/domain` already had `allocate(total, weights)` doing exact largest-remainder-method splitting (built for some other purpose entirely) — equal parts is just `allocate(remaining, [1, 1, ..., 1])`, so no new domain code was needed. `PaymentsService.suggestEqualSplit` wraps it over the invoice's *remaining* balance (not the full total, so it stays correct after a partial payment) and is read-only — a suggestion for the cashier/UI, never a payment by itself; collecting each share is still an ordinary `record` call.
- New routes: `POST /orders/:id/invoices/split-by-seat`, `POST /orders/:id/invoices/split-by-items` (body `{ deviceId, groups: string[][] }`), `GET /orders/:id/invoices` (the full list), `GET /invoices/:invoiceId/split?parts=N` (equal-split suggestion). `order_items` also gained `invoiceId` in its own API response (`OrderItemSchema`) so a POS UI can show which items are already billed on another check during a split-by-item flow.
- Tested at the service and e2e layers: `invoices.service.test.ts` gained item-scoped generation (bills a subset, leaves the rest billable), rejection of already-invoiced/foreign item ids, `splitBySeat` (distinct seats, seat-less items sharing one invoice, rejects when nothing's left to split), `splitByItems` (caller groups, rejects an empty group), and `listByOrderId` returning every split invoice. `payments.service.test.ts` gained `suggestEqualSplit` (exact remainder distribution, scoped to the remaining balance after a partial payment, rejects non-positive parts, rejects a missing invoice). `apps/api-pos/src/invoices.e2e.test.ts` and `payments.e2e.test.ts` gained the same split-by-seat/split-by-items/equal-split cases over real HTTP.

### P2-22

Add bill-level and item-level discounts with limits, reason codes and manager approval. This is the first task to actually call `ManagerPinService` (P1-13's server-authoritative half, built long ago with nothing real to wire into) — a discount above the restaurant's own-authority limit is exactly the "sensitive action" that module was always meant to gate.
- **Limits, not a hard ceiling.** `discount_limit_settings` (one row per restaurant, no branch scoping — nothing in this task calls for a per-branch limit) holds `maxUnapprovedPercentBasisPoints`/`maxUnapprovedAmountMinor`, each independently nullable. Nullable means "no auto-approval for that discount type at all," not "unlimited" — the safer default (rule 6: never under-report a sale), same reasoning `tax_settings` defaults to the more conservative pricing mode rather than guessing in the business's favor. A restaurant that hasn't configured this yet requires manager approval for every single discount.
- **Manager approval, wired for real.** `DiscountsService.resolveDiscount` computes the discount amount, compares it against the configured limit (percent-type discounts check the percent cap; fixed-amount discounts check the resulting minor-unit amount against the amount cap), and if it exceeds the limit, calls `ManagerPinService.approve({..., requiredPermission: "pos.discount.approve", action})` directly — the same "caller resolves its own permission" pattern that service's docstring always described, now with a real caller. A new `pos.discount.approve` permission (seed.ts, granted to `branch_manager`/`owner`/`super_admin`, same tier as the already-pre-seeded-but-unused `pos.void.approve`/`billing.refund.approve`) is what the approving user's role must hold.
- **A discount is a recorded reduction, never a price rewrite** (rule 6). `order_items` and `orders` each gained four columns — `discountPercentBasisPoints`/`discountAmountMinor` (a CHECK constraint enforces at most one is ever set, same convention as the productId/variantId exclusivity check), `discountReasonCode`, `discountApprovedByUserId` (null when within the cashier's own authority, set to the approving manager otherwise) — alongside the untouched `unitPriceMinor`/order total. `computeOrderTotal` (shared by `OrdersService.getTableTab` and invoice generation) now subtracts each item's own discount via `packages/domain`'s existing `applyPercentageDiscount`/`applyFixedDiscount` — no new domain math was needed, that module already clamps a discount to never exceed the amount it's applied to. `InvoicesService.generate` applies the bill-level discount the same way, but only for a whole-order invoice (no `itemIds`) — a split-by-item/seat invoice (P2-21) has no single "whole bill" to discount, so bill-level discounts are deliberately skipped there; item-level discounts are the right tool for a split bill instead, since they travel with their item into whichever split invoice it lands on.
- **Reason codes are a restaurant-defined list, not free text** (`discount_reason_codes`, an inclusion list unlike `payment_method_settings`' exclusion-list convention — there's no sensible universal default reason to fall back to). A discount is rejected outright if its reason code doesn't exist or has been deactivated.
- New routes: `POST`/`DELETE /orders/:id/discount` (bill-level) and `.../orders/:orderId/items/:itemId/discount` (item-level), both `pos.sell`-gated in `api-pos` — the manager-PIN escalation happens inside the service, not via a different route permission. `GET`/`PUT /discount-reason-codes` and `/discount-limits` in `api-admin`'s `CatalogModule`, same `menu.manage` tier as tax/service-charge/payment-method settings. `DiscountsService` needs `ManagerPinService` (+ its own `PermissionsService`), so both `OrdersModule` and `CatalogModule` provide their own copies directly, same "don't import the whole sibling module" reasoning as every other shared stateless service in this codebase (`PriceResolutionService`, `TaxCalculationService`, etc.).

### P2-32

Build a persistent print queue with retry, failure alerts and reprint marked as a copy. Sits directly on top of P2-31's `escpos.rs`/`printer_transport.rs`; still no real caller for any of it (P2-33's receipt templates are what will actually build real receipt bytes for a real sale).
- New local SQLite table `print_jobs` (migration `0007_print_queue.sql`, registered as version 7 in `db.rs`'s `MIGRATIONS`) — enqueueing is a plain `INSERT`, so a job survives an app crash or restart the same way `operation_log`'s writes already do (rule 13). Columns: `printer_connection` (JSON `PrinterConnectionConfig`), `data` (raw ESC/POS bytes, `BLOB`), `status` (`pending`/`printing`/`failed`/`done`/`dead_letter`), `attempts`/`max_attempts`, `next_attempt_at` (backoff scheduling), `last_error`, `is_copy`.
- **The one design point that actually mattered for rule 14** ("a printer failure must never block a sale"): `print_queue.rs`'s functions (`claim_due_jobs`, `mark_succeeded`, `mark_failed`) are each a short, separate SQL statement taking a bare `&Connection` — none of them perform the actual network/USB send. `printer_commands.rs`'s `process_print_queue` is what stitches them together, and deliberately releases the app's local-DB mutex *before* calling `PrinterTransport::send` for each claimed job, re-acquiring it only afterward to record the outcome. Without that separation, one slow or hung printer (rule 15 bounds how slow, never to zero) would hold the same mutex every other local DB read/write in the app shares — including, eventually, whatever writes a sale — for the full timeout duration.
- Retry: capped at `max_attempts` (default 5) with exponential backoff between attempts (`5s * 2^attempt`, capped at 300s) — once exhausted, the job moves to `dead_letter` rather than retrying forever, same shape as the server-side outbox's capped-retry-then-dead-letter (P1-30), though the two are entirely separate queues (local SQLite vs. Postgres) with no shared code — there's nothing to reuse across them, just the same design shape.
- **Reprint is marked on the actual printout, not just a database flag**: `enqueue_reprint` re-renders the job by prepending a `*** COPY ***` banner (via P2-31's `ReceiptBuilder`) onto the original bytes before enqueueing, and flags `is_copy` for reporting — so a reprint is visibly distinguishable on the paper itself, which is what actually matters for a cashier or auditor, not a column only a report would ever read.
- **"Failure alerts," honestly scoped**: `get_print_queue_status`/`list_print_jobs` are the backend primitives a frontend would poll to show a banner once `dead_letter > 0` — same polling pattern as P1-29's `SyncStatusIndicator`. No frontend polls them yet; there's no printer-setup screen (P2-35) or receipt flow (P2-33) to surface an alert from yet, so this documents the intended integration point rather than faking one.
- Tested via `print_queue.rs`'s own `#[cfg(test)]` unit tests against an in-memory SQLite connection seeded with the real migration SQL (same convention as `pending_work.rs`'s tests): enqueue creates a pending job, a reprint's stored bytes actually contain the COPY banner and the original text, claiming marks a job `printing` and returns its bytes, claiming twice doesn't reclaim an already-printing job, success sets `done`, failure retries then dead-letters once `max_attempts` is hit, a freshly-failed job isn't immediately due again (backoff), and `queue_status` counts correctly by status. Not run this session — same pre-existing OpenSSL/Perl build blocker as the rest of this crate's native deps; CI is authoritative.

### P2-36

Add hub mode to the desktop app: local WebSocket and HTTP server with paired devices only. ### P2-37

Add automatic hub discovery on the local network, with manual IP as a fallback. Builds directly on P2-36 — no new Cargo dependency, no new server; this is a third background listener added to the same `hub_server::start` and a client-side broadcaster any terminal can call.
- **The protocol (`hub_discovery.rs`, new, std-only)**: a terminal broadcasts one UDP packet to `255.255.255.255:47999` (the fixed, well-known `DISCOVERY_PORT` — deliberately separate from P2-36's HTTP/WS ports, which are per-install and can be anything) carrying its own `restaurantId`; every hub on the LAN listening on that port replies only if the request's `restaurantId` matches its own, with its `{deviceId, branchId, httpPort, wsPort}` — a foreign restaurant's terminal in the same physical building (a shared plaza, say) gets silently ignored, the same tenant-isolation instinct as everywhere else in this codebase, even though a discovery hint isn't actually sensitive data. Malformed or unrelated UDP traffic on the port (anything that doesn't start with this protocol's magic prefix, or doesn't parse as JSON) is silently ignored rather than risking a panic in a background thread that's otherwise invisible to the rest of the app.
- **Wired into the existing hub, not a separate "discovery mode"**: `hub_server::start` now takes an extra `HubIdentityInput` (device/restaurant/branch id — supplied by the caller, same as `menu_commands.rs`'s convention of the frontend passing in what it already knows) and a `discovery_bind_port`, binds the UDP socket itself (so the real ports can be read back before spawning anything, same "bind first, serve in a thread" shape P2-36 already used for HTTP/WS), and constructs the full broadcast identity using the HTTP/WS ports it *actually* bound — so a hub started with port 0 (OS-assigned) still broadcasts the right numbers, not the caller's original request. `HubServerHandle` gained a third thread and a `discovery_port` field, joined on `stop()` along with the other two.
- **`refresh_hub_roster`'s "live swap" pattern (P2-36) has a parallel here that was deliberately NOT built**: a running hub's broadcast identity is fixed at `start_hub` time and never changes without a restart (unlike the roster, which `refresh_hub_roster` can swap live). Nothing about this task calls for identity to change while running — a device/restaurant/branch id doesn't change mid-session — so there's no "live identity swap" to add; flagged here only so it doesn't look like an oversight.
- **Manual-IP fallback (`check_hub_reachable`)**: deliberately NOT an identity check — it only confirms `GET /health` answers at the given address, same trust model P2-35's printer setup screen already uses for a typed IP (the user already knows this is the right machine; the check just proves it's reachable). A stricter check would need `/health` to return identity info the way the UDP protocol does, which would mean changing P2-36's already-reviewed `/health` handler — deliberately avoided to keep this task's blast radius to new files plus `hub_server::start`'s signature only.
- New Tauri commands (`hub_commands.rs`): `discover_hubs(restaurantId, timeoutMs)` (an empty result is routine — no hub running, or a network that blocks broadcast — never an error) and `check_hub_reachable(ip, httpPort)`. `start_hub` gained the three identity parameters; `HubStatus` gained `discoveryPort`. Still no frontend screen calling any of this — same "nothing real to connect *to* yet" scoping as P2-36, since P2-38 is what will actually give a hub connection a purpose.
- Tested via `hub_discovery.rs`'s own real-socket unit tests (same posture as P2-36's `hub_server.rs` — genuinely testable with local UDP sockets, no hardware needed): request/reply parsing round-trips, garbage input is ignored rather than erroring, a live responder is actually discoverable, a responder never replies across a restaurant-id mismatch, and an empty network returns an empty list rather than an error. `hub_server.rs` gained one integration test confirming that starting a hub also makes it discoverable with its real (not requested) ports. Same honesty flag as P2-36: this was written from memory of `tungstenite`/`tiny_http`'s general shape, not confirmed by a compiler this session — CI is authoritative, more so here than most of this phase's Rust work.

### P2-38

Share orders, table status and kitchen tickets between devices through the hub while offline. The task where the hub (P2-36/37) actually starts doing something — until now it only proved a connection could be authenticated.
- **The real constraint this had to work around**: no local order/table-status/kitchen-ticket schema exists anywhere in this app yet — P2-12's cart is still pure React state with no server order behind it, and Phase 3's real kitchen-ticket/inventory schema doesn't exist. Building full order objects to "share" would mean inventing Phase 3's schema early, which CLAUDE.md rule 8 explicitly says not to do. So this task builds the generic transport + relay + conflict-resolution primitive that a real order/table-status/kitchen-ticket feature will publish *into* later (the same thing P2-06's "out-of-stock marking" docs already flagged as blocked on "P2-36-39's hub" existing) — not the business objects themselves.
- **Conflict resolution (`hub_state.rs`, new, pure)**: one entry per `(entityKind, entityId)`, carrying a caller-supplied monotonic `version` (in practice a millisecond timestamp) and an opaque `payload` this layer never inspects. `apply_if_newer` is the one rule the whole relay exists to enforce — a version that isn't strictly greater than what's already stored for that entity is silently dropped, never applied or rebroadcast, whether it's a genuine race between two devices or a duplicate relay. This is last-write-wins by caller-supplied version, not a CRDT or true merge — explicitly adequate for a LAN convenience layer syncing *display* state while offline, not a replacement for rule 3's real server-side recalculation once connectivity returns.
- **Persistence**: a new local SQLite table `hub_shared_state` (migration 9, `0009_hub_shared_state.sql`), so the hub's current view of the branch survives its own restart, same "don't lose what's already there" reasoning P1-22's watchdog/pending-work and P2-32's print queue already apply to other local state. A new `db::open_secondary` (small addition to `db.rs`) gives the relay's background threads their own connection to the same encrypted file — safe because this app has been WAL-mode since P1-19 — so they never contend with `DbState`'s connection, which every ordinary Tauri command already locks for the length of its own call.
- **The relay itself (`hub_server.rs`, substantially rewritten)**: a WebSocket connection is no longer a one-shot "say hello, then close" — once authenticated, it stays open, immediately receives a `snapshot` of everything already shared, and from then on exchanges `state_update` messages. An update from one connection is applied (if newer), persisted, and broadcast to every OTHER connected device, never echoed back to its own sender. `HubServerHandle::publish` is the identical path for the hub's own local changes — it never has to fake a loopback connection to itself. Full duplex without an async runtime: each connection's socket gets a short read timeout, so its loop alternates between "anything to read from this client" and "anything queued by other threads to push to this client," same polling shape already used for the HTTP/WS accept loops.
- **A real bug found and fixed while building this, not shipped**: the first draft only made `stop()` join the three FIXED listener threads (HTTP/WS accept/discovery) — every already-open per-connection thread kept running forever afterward, since nothing told it to stop, leaking a thread and a live socket per connection every time hub mode was stopped and restarted. Fixed by threading `stop_flag` into each connection's own loop too, closing its socket cleanly once noticed (within one `WS_READ_POLL_TIMEOUT`, documented as an acceptable brief wind-down rather than something `stop()` blocks on, since connections — unlike the three fixed listeners — don't have a fixed set of handles to join).
- **The non-hub side needs no Rust at all**: `apps/desktop/src/shared/hub-client.ts` (new, pure TypeScript) connects with the browser's own native `WebSocket` API directly from the frontend — only the hub itself runs server code; everything connecting TO it (P2-37's discovery already established this split, this task's client confirms it) is just a browser WebSocket client. `connectToHub` exposes `onHello`/`onSnapshot`/`onUpdate`/`onClose`/`onError` callbacks and a `send`/`close` pair; malformed or unrecognized messages are ignored rather than allowed to crash the connection.
- New Tauri command `publish_hub_update` (hub_commands.rs) — only meaningful while this terminal IS the hub; a non-hub device publishes instead by calling `hub-client.ts`'s `send()` on its own outgoing connection, no Rust involved. `entity_kind` stays free-form at this layer (the three the task names are `order`/`table_status`/`kitchen_ticket`, but this transport never validates which).
- Tested: `hub_state.rs`'s own unit tests (apply-if-newer accepts first/rejects stale/accepts newer, independent tracking per entity kind, persist/load round-trip, upsert-not-duplicate). `hub_server.rs` gained a full relay test suite (hello-then-snapshot on connect, a pre-existing shared entry appears in a new connection's snapshot, an update relays to another connection but never echoes to its own sender, a stale update is silently dropped and never relayed, `publish` applies/persists/broadcasts a hub-originated update) alongside the already-existing P2-36/37 auth/discovery tests. `hub-client.ts` has its own vitest suite (connects to the right URL with the token query-encoded, dispatches each message type to its handler, ignores invalid JSON and unrecognized message types without throwing, `send`/`close` behave correctly) using a hand-rolled fake `WebSocket` (same `vi.stubGlobal` convention as `api-client.test.ts`), run through a bug found mid-writing where the test's own socket reference pointed at the wrong connected instance — fixed before it could hide a real failure.
- **Not run this session**: the Rust side (same pre-existing OpenSSL/Perl build blocker as every Rust file this phase, now compounded by hand-written, not compiler-verified, use of `tungstenite`'s lower-level message/stream APIs — flagged as this task's highest-uncertainty area for CI to settle) and the new frontend tests.

### P2-39

Make terminals keep billing if the hub fails, and catch up when it returns. The last task in Branch hub — closes out the section.
- **"Keep billing" needed no new code at all, and that's worth stating explicitly rather than assuming**: a sale goes through `OrdersService` → local SQLite (`operation_log.rs`) → the real server sync (`sync_client.rs`), and none of that path calls into `hub-client.ts`/`hub_server.rs` anywhere — the hub relay (P2-36/37/38) is purely the *convenience* layer for table status/kitchen tickets, never in the critical path billing depends on. Rule 14 ("a broker/report/printer/external service failure must never block a sale") already held here by construction the moment P2-38 was built with billing never routed through it; this task verified that boundary rather than rebuilding anything to enforce it.
- **"Catch up when it returns" is what P2-38's `hub-client.ts` was still missing**, and is this task's real work:
  - **Jittered-backoff auto-reconnect** on any unexpected drop (not a deliberate `close()`) — same shape as P1-35's server-sync backoff, including the same reasoning for the jitter: if a hub comes back after an outage, every terminal that was waiting on it shouldn't all pile back in at the exact same instant. Backoff resets to its base delay after a successful reconnect, not after every individual attempt.
  - **A bounded outbox** for anything `send()`'d while disconnected — keyed by `entityKind:entityId` rather than an append-only list, so a newer pending update for the same entity simply replaces an older one instead of queuing both. This is free to do safely because the relay is already last-write-wins by `version` (hub_state.rs, P2-38) — there's nothing gained by keeping a stale queued entry around — and it's what keeps the outbox's size bounded by how many *distinct* entities were touched while offline, not by how long the outage lasted (an unbounded list would have been a real memory-growth risk across a long outage otherwise). Flushed in full the instant the reconnected socket opens.
  - **`onConnectionStateChange`** (`"connecting" | "open" | "reconnecting" | "closed"`) replaces P2-38's original `onClose`/`onError` handlers with one signal a frontend can show directly (e.g. "hub offline, billing continues locally") without maintaining its own retry state.
- **Deliberately NOT handled, and said so rather than guessing**: a hub whose LAN address changed while it was down (a new DHCP lease after a reboot, say) — reconnection targets the same `host`/`wsPort` it was originally given. A caller that keeps failing to reconnect for an unusually long time is expected to re-run P2-37's discovery and call `connectToHub` again with a fresh address; this module doesn't invent its own re-discovery policy or threshold for that, since CLAUDE.md doesn't specify one and guessing one felt like overreach for what the task actually asked for.
- No Rust changes this task — everything lives in `apps/desktop/src/shared/hub-client.ts` (substantially rewritten) and its test suite, consistent with P2-38's finding that the non-hub side needs no Rust at all.
- Tested: a rewritten `hub-client.test.ts` using fake timers (`vi.useFakeTimers`) and a `Math.random` pin (to make jittered-delay assertions deterministic rather than occasionally flaky) — connection-state transitions, each message type dispatching to its handler, immediate send when open vs. queuing when not, outbox dedup replacing an older queued entry for the same entity, multiple distinct entities all flushing, increasing backoff across repeated drops, backoff resetting after a successful reconnect, outbox flushing on reconnect, and `close()` both stopping future reconnect attempts and canceling an already-scheduled one.
- **Not run this session**: these frontend tests haven't been executed — same "skip verification until asked" posture as the rest of this session.

### P2-40

- **Reused `packages/domain`'s already-trusted money functions rather than inventing new math**: the void report's "value of what was voided" and the discount report's per-item discount amount are both computed via `multiply`/`add`/`sum` (base + modifiers) and `applyPercentageDiscount`/`applyFixedDiscount`, the exact same functions `OrdersService.computeOrderTotal` and `DiscountsService` already use at apply time — `computeOrderTotal` itself was also exported from `nest-core`'s `index.ts` for the first time this task (it existed since P2-23 but was never re-exported). Reports recompute rather than read a stored "discount amount" column because none exists: `order_items`/`orders` only ever stored the discount's *configuration* (percent or fixed amount), never its resolved minor-unit effect — same reasoning the original P2-22/23 work never needed to store a redundant derived figure either.
- **Scope decision, stated explicitly rather than silently narrowed**: the discount report covers item-level discounts only, not bill-level (order-level) ones. Recovering a bill discount's minor-unit effect needs the SAME non-voided, already-item-discounted subtotal recomputation `DiscountsService.applyBillDiscount` does at apply time — real money math, but a materially bigger lift than every other figure in this "basic" report (which are each either an already-stored total or one self-contained per-item calculation). - **A second documented approximation**: the discount report windows by `order_items.updatedAt`, since discounts (unlike voids, which got their own `voidedAt` column in P2-23) have no dedicated "discount applied at" timestamp — an item touched for an unrelated reason on a different day after being discounted could in principle land in the wrong day's report. Acceptable here, not for anything that needs to balance to the rupee.

### P2-41

Index SQLite for POS searches, and use list virtualization for long menus and order lists. First task in Phase 2's Performance section.
- **SQLite indexing, the honest version**: checked what menu_cache.rs's own queries actually filter/sort by. Four composite indexes replace the old single-column ones, each covering both the `WHERE` filter and the query's own `ORDER BY` so SQLite serves "filter + already in sort order" straight from the index, no separate sort step — `menu_products(category_id, sort_order, name)`, `menu_categories(sort_order, name)`, `product_modifier_groups(product_id, sort_order)`, `modifier_options(modifier_group_id, sort_order)`. These cover the category-tap and modifier-group-listing paths, which happen far more often per order than typing a free-text search.
- **The free-text search is deliberately left as a full scan, and said so rather than guessing at a fix**: `list_products`'s `lower(name) LIKE '%term%'` (name/sku/barcode substring match) has a leading wildcard, which can never use a plain b-tree index in SQLite regardless of what's indexed — a property of the query shape, not a missing index. The correct tool is an FTS5 virtual table with the trigram tokenizer (genuine index-accelerated substring search), deliberately not added: whether this crate's bundled SQLCipher build has that tokenizer compiled in couldn't be confirmed without a `cargo build` this session, and guessing wrong would silently break menu sync rather than just being slow. At a single branch's realistic menu size (tens to a few hundred products), the existing full scan isn't expected to be a measurable bottleneck — rule 9's "measure before optimizing," where the "measurement" here is reasoning about realistic row counts rather than a profiler run that would need a running app to take.
- **List virtualization — asked the user first, since it meant a new dependency.** CLAUDE.md rule 8 says not to add technology outside the approved stack without asking; virtualization needed either a library or a hand-rolled implementation, and ProductGrid's responsive multi-column grid (2/3/4 columns across Tailwind breakpoints) is genuinely hard to virtualize correctly by hand without a real browser to verify against. Presented three options (library / hand-roll / skip with reasoning); the user chose `@tanstack/react-virtual` — same vendor as the already-installed `@tanstack/react-query`, actually installed via `pnpm install` this task (not just added to package.json).
- **A size threshold, not virtualization everywhere**: both `ProductGrid` (threshold 60 products) and `CartPanel` (threshold 40 lines) keep their ORIGINAL, already-tested plain-rendering code path for anything below the threshold, and only switch to `useVirtualizer` above it. This was a deliberate design choice, not just an optimization nicety: virtualization has its own overhead (measuring, absolute positioning, a resize listener) that isn't worth paying for the common case (a modest menu, a typical few-line order), AND it means every EXISTING test fixture (2 products, 1-2 cart lines) continues to exercise the exact unchanged original code path, so none of those tests needed to change.
- **ProductGrid's virtualization groups products into rows** (`chunk(products, columnCount)`) since `@tanstack/react-virtual` only windows one dimension — `columnCount` is tracked via a `resize`-listening hook mirroring the exact Tailwind breakpoints (640px/768px) the grid's own CSS classes already use, so the JS-computed row grouping and the CSS-computed visual column count never disagree. **CartPanel's virtualization measures each line's real rendered height** (`measureElement`) rather than assuming a fixed one, since a line's height genuinely varies with how many modifiers it carries.
- **A real HTML-validity bug caught and fixed while writing this**: the first draft of CartPanel's virtualized branch wrapped each `<li>` row in an extra positioned `<div>` so the row component could stay unchanged — but a `<div>` is not a valid direct child of `<ul>`. Fixed by extracting the row's inner content into a separate `CartLineContent` component, reused by both an ordinary `<li>` (small-cart path) and the virtualized branch's own directly-positioned `<li ref={measureElement}>` (no wrapper `<div>` at all).
- Tested: `ProductGrid.test.tsx` and a new `CartPanel.test.tsx` each gained a "virtualized" describe block (100+/80+ items) alongside their existing small-fixture coverage (left completely unchanged, confirming the threshold logic actually preserves the old path) — stubbing `ResizeObserver` (not implemented in jsdom at all; `@tanstack/react-virtual` would throw without it) and `HTMLElement.prototype.clientHeight` (jsdom's real layout always reports 0) so the virtualizer computes a non-trivial visible window instead of rendering nothing. Each virtualization test restores the `clientHeight` override afterward via the original property descriptor, to avoid leaking a global prototype mutation into other test files sharing the same worker.
- **Honesty flag, same posture as this phase's riskier Rust work**: jsdom has no real layout engine, so these virtualization tests are a best-effort proof that "a subset renders, not everything" and that interactions (click, remove) still work on whatever IS rendered — not a guarantee that the exact visible window `@tanstack/react-virtual` computes in a real browser matches what jsdom's stubbed numbers produce. Not run this session either way; CI is authoritative.

### P2-43

Cache versioned menus and prices in Redis, and clear the cache when a new version is published. The first task that actually connects to section 3's "Cache and jobs: Valkey or Redis" stack entry — P1-02's docker-compose has provisioned Valkey since Phase 1, but nothing in this codebase talked to it until now.
- **What's actually expensive, found by reading the code rather than guessing**: `SyncSnapshotService.loadMenu` (P2-11) does a full per-branch catalog read, then an N+1-shaped loop calling `PriceResolutionService.resolvePrice` individually for every product/variant/modifier-option across all three order types — re-run on EVERY terminal sync even when nothing about the menu or prices has changed since the last one. That recomputation, not the outer snapshot envelope, is what gets cached.
- **`version`/the signature are still minted fresh on every call, cache hit or not** — P2-17 already relies on the snapshot's `version` field as a "prices as of {this moment}" display, and changing that meaning to "only changes when the menu changes" would have quietly broken that already-shipped feature. Caching only the `SnapshotMenu` content (not the full envelope) keeps both behaviors correct at once: a cache hit is just as fast, and still honestly timestamped as "synced right now."
- **New `RedisModule`** (mirrors `DbModule`'s exact shape — a `Symbol` token, a `forRoot` static factory, `global: true`) wraps a single `ioredis` client with `lazyConnect`/`maxRetriesPerRequest: 1`/`enableOfflineQueue: false` and a swallowed `error` listener — a cache must never be the reason a sync fails (rule 14), so a slow/unreachable Redis fails one call fast rather than retrying and blocking the fallback path that was going to compute fresh anyway.
- **New `MenuSnapshotCacheService`**: `get`/`set` fail soft on any Redis error (always treated as a miss), keyed by `(restaurantId, branchId, generation)`. `invalidateRestaurant` — "clear the cache when a new version is published" — bumps a per-restaurant generation counter with one atomic `INCR` rather than deleting keys directly: every existing cached entry's key embeds the generation current when it was written, so bumping it makes them all unreachable in one call without needing to enumerate branches or scan/delete a key pattern (which Redis has no efficient, safe way to do in production). Stale entries aren't actively deleted; they age out via a 5-minute TTL once nothing reads them.
- **Scope decision, stated explicitly**: only `PriceListsService.publish` actually calls `invalidateRestaurant` — the dominant, most consequential "a new version exists" event, and the one this task's own wording ("when a new version is published") names directly. A brand-new product, a renamed category, an edited modifier group do NOT explicitly invalidate; threading this cache into every one of Phase 2's already-reviewed catalog services for a staleness window the 5-minute TTL already bounds wasn't worth the blast radius. Documented as an accepted gap, not an oversight — the same posture as this phase's other deliberately-scoped caching/indexing decisions (P2-41's SQLite work took the identical stance).
- **A real design question resolved explicitly**: the invalidation call in `publish()` fires AFTER its own `withTenant` transaction has committed, not inside it — a cache bump isn't something that should roll back if, say, the audit write inside that transaction failed, and bumping it before the publish is durably committed would let a reader see a cleared cache for a price list that then fails to publish at all.
- **A real compile-breakage risk found and avoided before it happened**: `PriceListsService` is directly instantiated with exactly two constructor arguments in 12 existing test files across this package. A REQUIRED third constructor parameter would have broken every one of them. Made it `@Optional()` instead, same precedent as P2-30's `OrdersService.businessDaysService` — `SyncSnapshotService` has only one direct-instantiation call site (its own test file, updated here), so its new cache dependency is a plain required constructor param instead; no reason to weaken that one too.
- Wired into both existing app processes: `RedisModule.forRoot({ url: process.env.REDIS_URL ?? "redis://localhost:6379" })` added to `api-admin`'s (for `PriceListsService`, via `CatalogModule`) and `api-pos`'s (for `SyncSnapshotService`, via `SyncModule`) `AppModule`s. `REDIS_URL` is a new env var, following the exact `APP_DATABASE_URL`/`JWT_SECRET` naming convention already used everywhere else in this codebase.
- Tested: a new `menu-snapshot-cache.service.test.ts` against a REAL local Redis/Valkey (round-trip, invalidation makes an entry unreachable, a fresh `set` after invalidation is cached again, one restaurant's invalidation never touches another's) plus a dedicated fail-soft suite pointed at a deliberately unreachable address, confirming every method resolves harmlessly rather than throwing. `sync-snapshot.service.test.ts` gained a caching-behavior block: a category added after the first `buildSnapshot` call stays invisible (stale, cached) until a price-list publish invalidates it, and confirms one restaurant's invalidation never affects another's cached menu. `price-lists.service.test.ts` gained a mock-based test confirming `publish()` actually calls `invalidateRestaurant` with the right restaurant id when a cache is provided.
- **Honesty flag specific to this task**: the two new caching-behavior tests in `sync-snapshot.service.test.ts` and all five in `menu-snapshot-cache.service.test.ts`'s first block genuinely need a reachable Redis/Valkey to pass — unlike every other test in this session, which stays correct even if its target service happens to be misconfigured, these specifically assert on cache-hit/-miss behavior that only exists when the cache is real.
